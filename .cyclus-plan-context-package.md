# Context Package — saturate#9: node-readiness precondition check

## The gap (confirmed against current `main`, not stale worktree state)

`main` today is explicitly **Phase 1: single-node** (per `scheduler.py`'s own
module docstring). The dispatch path is:

```
scheduler_tick() → _dispatch() → _launch_runner() [subprocess.Popen]
                                        → runner_proc.main()
                                              → queue.claim()
                                              → run_turn(task_id, queue)  ← crashes here
```

**Zero readiness verification exists anywhere in this path.** `_dispatch()`
sorts pending tasks by `dispatch_score()` and spawns the winner via
`subprocess.Popen` with no precondition check. `SaturateTask` *declares*
`num_gpus: float` and `required_node_class: Optional[str]` (task.py:52-54)
but **nothing in scheduler.py, runner_proc.py, or runner.py ever reads
either field.** They're schema decoration today.

**The failure mode is worse than "crash once":** `runner_proc.main()`
wraps `run_turn()` in a bare `except Exception`, prints the traceback,
calls `queue.requeue(task_id)`, and exits 1 (lines 77-89). `requeue()`
(queue_sqlite.py:493) unconditionally sets `status='pending'` — no retry
counter, no failure classification, despite `SaturateTask.max_retries`
existing as a declared-but-unused field. **A task that fails because the
environment can never satisfy it (missing GPU, missing Python package)
gets requeued and retried forever**, burning a scheduler tick and a
subprocess spawn every cycle, indistinguishable in the queue from a task
that's making real progress.

Confirmed real, not theoretical: a MiniCPM-o finetuning smoke run crashed
on `ModuleNotFoundError: No module named 'datasets'` on gb10 — exactly
this failure class, caught only because a human was watching.

## Doctrine and Principles (this repo's own governing documents — read in full)

`DOCTRINE.md` has a **reserved, explicitly empty Article VI** slot:
> "Not yet an article — tracked, not written... This slot stays empty
> until #9 lands a fix... When #9 closes, this section gets written from
> what the fix actually established."

Do not write Article VI. That is out of scope for this plan — it happens
after the fix ships, by whoever closes #9, from what actually shipped.

Relevant existing principles this plan must not violate:
- **P3** (Article III, Conformance not assumption): verify external
  contracts at the boundary rather than assuming their shape. This gap is
  the same discipline applied to *node capability* instead of *schema*.
- **P4** (Article IV, Auditability): "the queue is the only source of
  truth... nothing state-bearing lives elsewhere." Any readiness state
  this plan introduces (e.g. "this node lacks X") must be queue-durable,
  not held only in a log line or a running process's memory.
- **P9**: loop-spec is a shared contract Saturate proposes into, never
  forks locally. If the fix requires a new `loop-spec` field (e.g. a
  `requires`/`preflight` block on `ExecutorSpec`), that's a `loop-spec`
  PR first, a Saturate consumer-side change second — not a Saturate-local
  schema fork.

## The actual design question for the Planner

What is the minimal, doctrine-consistent mechanism that:
1. Declares node capability requirements on a task (some of this already
   exists unused: `num_gpus`, `required_node_class` on `SaturateTask`)
2. Verifies those requirements against the actual local environment
   *before* `_launch_runner()` spawns the subprocess — not after it
   crashes inside `run_turn()`
3. On a genuine mismatch, marks the task with a **distinct terminal or
   held state** — not a silent `requeue()` back to `pending`, which is
   indistinguishable from a transient failure and retries forever
4. Is queue-durable (P4) and doesn't require a `loop-spec` fork (P9) if
   it needs new spec fields

Deliverable: a concrete implementation plan (files touched, new
functions/fields, acceptance criteria per task) that could close #9 for
real — i.e., produce the incident Article VI gets written from.
