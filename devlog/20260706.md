# Devlog — 2026-07-06

*The day Saturate was born and built itself.*

---

## Where we started

A conversation about whether Ray was the right foundation for a distributed
compute fabric. By the time the question was fully examined, the answer was
no — and the real question had sharpened into something more interesting: what
would a system built specifically for agentic loops look like, starting from
first principles?

## The thesis

The world moved to GPU. CPU is underutilized.

Most agentic loops don't need a GPU — they coordinate, call frontier AI APIs,
run tools, measure results. That's CPU and network. The bottleneck nobody is
talking about is CPU capacity, and across any fleet of machines it is enormous
and almost entirely idle.

The other insight: current loop engineering scales **down**. One orchestrator,
sub-agents, one machine. Nobody has built the distributed layer. Saturate is
the distributed layer.

**The unit of work is a loop** — not a task, not a job. A loop has a goal, a
metric, a hypothesis engine, and a terminal condition. It iterates. It keeps
what works and reverts what doesn't. It runs until externally stopped or until
it finds a plateau.

## The architecture that emerged

Spent the afternoon designing in parallel: VISION.md, ARCHITECTURE.md,
requirements doc. The key decisions:

**Four-operation interface:** `post`, `claim`, `write_state`, `complete`.
Any producer — Cyclus, a CLI, a shell script — targets this interface.
Any backend — file-based, SQLite, PostgreSQL, eventually Nomad — implements it.
Workers don't know what's underneath.

**Six sealed loop kinds:** `metric-optimization`, `task-execution`,
`information-seeking`, `clarification`, `consensus`, `selection`. Each kind has
typed turn results and terminal conditions. `clarification` is structurally
human-gated — only a human `complete()` ends it. This is a type property, not
a configuration option.

**SQLite → PostgreSQL queue.** No Ray, no Kubernetes, no Temporal. Embedded
SQLite for single-node development (no server process), PostgreSQL with
`SELECT FOR UPDATE SKIP LOCKED` for concurrent multi-node fleet. Same schema,
same four operations, configuration switches between them.

**Nomad for fleet management.** Single binary, Linux and macOS native,
Tailscale-friendly, fractional CPU/GPU allocation, custom capability tags.
Routes loops to nodes; doesn't pool GPU across nodes for one workload.

**The Executor protocol.** The piece we almost missed entirely. Saturate defines
how to *run* a loop. The Executor defines *what agent runs it*. Three v1
implementations: `HermesExecutor` (Forge), `ShellExecutor` (any executable),
`HTTPExecutor` (any endpoint). Workers don't import a Saturate SDK.

Got external validation from Gemini on the requirements doc:
> *"This is an exceptionally well-written, clear, and realistic specification."*
Recommended exactly the stack we'd already converged on.

## The bootstrap thesis

The fastest path to a working Saturate is not to build it completely before
using it. Build the minimum slice that can run a loop, then run a loop that
builds the rest.

**Phase 0** (~380 lines, hand-written):
```
measure.py     four-outcome scalar metric primitive (improved/regressed/crashed/unchanged)
queue.py       file-based queue, atomic POSIX claim via os.rename
executor.py    Executor protocol — HermesExecutor + ShellExecutor
runner.py      one-turn loop runner with kind dispatch
cli.py         submit / run / run --loop / status
```

Used `omh-ralph-driver` to dispatch the Phase 0 work as parallel subagents.
Tasks 1/2/3 (measure, queue, executor) ran in parallel — all three green on
first run. Task 4 (runner) caught a real bug: baseline must be seeded on turn 0
even for `unchanged` outcome, or the loop runs forever returning unchanged.
Fixed before it landed.

49 tests. Zero failures.

Then submitted the first loop spec:

```bash
saturate submit goals/phase1-implementation.yaml
saturate run --loop <task_id>
```

## Phase 1 ran itself

The loop ran. Forge received the task message:

```
YOUR TASK FOR THIS TURN:
  SaturateTask dataclass

...full task body from plans/phase1.md...

Instructions:
1. Implement this task completely
2. Write SUCCESS: or FAILED: to hypothesis.md
3. Commit your work with git before exiting
```

One task per turn. Four tasks. Four turns.

```
turn 0: improved   →  SaturateTask dataclass + dispatch_score()
turn 1: improved   →  SQLite queue (SqliteQueue, SELECT FOR UPDATE SKIP LOCKED)
turn 2: improved   →  Scheduler tick + runner_proc.py
turn 3: terminal   →  saturate start command + integration tests
```

**139 tests. Zero failures.**

There were bugs along the way — the loop ran 300+ turns on the wrong job before
we added kind dispatch; the plan path resolved against the spec file directory
instead of cwd; the hermes CLI invocation was wrong (`run --message` instead of
`chat -q`); the success heuristic was inverted (defaulted to success instead of
requiring explicit `SUCCESS:` prefix). Each one caught, fixed, documented.

By 7:52 PM PDT, Saturate had bootstrapped itself.
